# Learning notes

Short explanations of the frontend techniques used in this project, written for a Laravel/React developer. Each entry: what it is, where it is used here, and the one thing that is easy to get wrong.

## Next.js 16: Cache Components

`cacheComponents: true` (in `next.config.ts`) replaces the old `fetch` cache options. A function or component marked `"use cache"` is cached and becomes part of the prerendered static shell; `cacheTag("home")` labels it so `revalidateTag("home", …)` can expire it on demand (our backend calls `POST /api/revalidate` after every admin edit). Anything that reads request data (`cookies()`, `headers()`, `searchParams`) must sit inside `<Suspense>` so the rest of the page can stay static.

## Admin auth: BFF + httpOnly cookie + proxy.ts

The browser never talks to Laravel's admin API and never sees the Sanctum token. `app/api/admin/login` (a Route Handler, i.e. server code) posts the credentials to Laravel, puts the returned token in an **httpOnly** cookie `hk_admin` (SameSite=Lax, Secure in production, 7 days) and answers only `{ data: { user } }`. Every later admin call goes to the same-origin **BFF** ("backend for frontend") catch-all `app/api/admin/[...path]`, which reads the cookie on the server and forwards to `{API_URL}/admin/<path>` with `Authorization: Bearer …`, streaming bodies so 30 MB uploads pass through. JavaScript can't read an httpOnly cookie, so an XSS bug can't steal the token, and since Laravel is only called server-side, CORS and token storage never come up. Because the browser sends the cookie automatically, non-GET BFF requests reject a foreign `Origin` header (CSRF guard). A Laravel 401 also deletes the cookie.

`proxy.ts` (Next 16's new name for `middleware.ts`) runs before `/admin/*` pages and only checks whether the cookie _exists_: no cookie → `/admin/login?next=…`, cookie on the login page → `/admin`. It's an optimistic redirect, not security. The real check is in the `(panel)` layout: `SessionGate` calls Laravel `/admin/me` with the token and `redirect()`s when it's dead. With Cache Components, anything that reads cookies must sit inside `<Suspense>`, so the sidebar/topbar stay static and only the gate streams in. The easy thing to get wrong: `await connection()` before the uncached `fetch`. Otherwise Next's runtime prerender stage (cookies available, uncached I/O not) reports a `Date.now()` error.

## Cache Components in practice: `"use cache"`, tags and on-demand revalidation

`lib/api.ts` marks each reader with `"use cache"`, `cacheLife("max")` and `cacheTag("home")`. At build time Next runs it once and bakes the result into the static HTML. When the admin saves, Laravel posts `{ tags: ["home"] }` to `app/api/revalidate/route.ts`, which calls `revalidateTag("home", { expire: 0 })`; the next visitor triggers a fresh render. Easy to get wrong: reading `cookies()`/`headers()`/`searchParams` (or `params` outside `<Suspense>` for dynamic routes) silently makes a route dynamic — check the `○ / ◐ / ƒ` markers in `next build` output.

## Filtering without JavaScript: radio inputs + `:has()`

The Journey tabs are real `<input type="radio">`s styled as tabs. A rule like `[&:has(#quest-filter-work:checked)_[data-group]:not([data-group=work])]:hidden` hides the other entries purely in CSS, so the filter works with JS off (Lite mode) and the phase-4 Flip animation can be layered on top of the same inputs.

## Draft Mode for previews of a static page

`draftMode().enable()` (in `/api/admin/preview`) sets a bypass cookie. The project page checks `(await draftMode()).isEnabled`; only then does it read the admin cookie and fetch the draft without cache. Everyone else gets the prerendered page — previewing never makes the public route dynamic.

## Pre-paint head script

Some UI depends on things only the browser knows (sessionStorage, localStorage, `prefers-reduced-motion`), but the page is static HTML. `components/game/splash/prepaint.ts` is a tiny function that `app/layout.tsx` inlines into `<head>` as `<script>` (via `fn.toString()`). The browser runs it while parsing, **before the first paint and before React**, and it writes `data-boot="play|skip"` and `data-lite="true|false"` on `<html>`. CSS reacts to those attributes, so the splash overlay is visible from the very first frame (or never), with no flash of the Hero and no layout shift. Showing the overlay is opt-in (`play`), so with JavaScript off it never appears, and a CSS failsafe animation hides it after 10 s if the bundle never takes over. Easy to get wrong: (1) `<html suppressHydrationWarning>` is needed because React didn't render those attributes; (2) a server component that imports a constant from a `"use client"` module gets a client reference, not the value, which is why the prefs key is duplicated in `prepaint.ts`; (3) in dev, React's Strict Mode remount wipes `<html>` attributes, so BootScreen re-runs the same function if they are missing.

## Splash timeline with real progress

The boot screen (`components/game/splash/BootScreen.tsx`) uses **one GSAP master timeline that is extended while it runs**: intro tweens first, then `tl.add(segment, tl.time()).play()` appends "ready" when loading finishes and the wipe when START is pressed. (A completed timeline accepts new children; `play()` continues from where the playhead stopped.) Endless loops (tips, START blink, the runner's legs) stay _outside_ the master timeline, because an infinite child would make it infinitely long. Progress is real: `criticalAssets.ts` weighs fonts (`document.fonts.ready`), the Hero image, the save cookie and the already-loaded payload. A `gsap.ticker` callback eases the displayed number toward `min(real target, time cap)` with a frame-rate-independent exponential (`1 - exp(-dt/τ)`). The time cap enforces the 2.2 s minimum (1.2 s for returning players) and the 5 s maximum, and since both inputs only grow, the number never goes backwards. The odometer is three reels moved with `translateY` in `em`, so it is all transforms and never re-renders React.

## MotionPath avatar scrubbed by scroll

`components/game/AvatarPath.tsx` draws an SVG trail in the right-hand gutter of Home and moves a pixel avatar along it with `motionPath: { path }` plus `scrollTrigger: { trigger: main, start: "top top", end: "bottom bottom", scrub: true }`. The walker div and the SVG share one coordinate system (both at the layer's 0,0, viewBox = pixel size), so no `align` is needed: GSAP applies the path's raw x/y as `translate()`. The geometry (gutter width, page height, chapter tops for the checkpoint flags) is measured into React state with a debounced ResizeObserver. `useGSAP({ dependencies: [geo], revertOnUpdate: true })` kills and rebuilds the tween whenever it changes, followed by `ScrollTrigger.refresh()`. Two things are easy to get wrong. Lenis already smooths the scroll, so `scrub: true` (not a number) avoids a second, laggy smoothing. And with Cache Components, Next keeps the previous route in the DOM (`display: none` inside `<Activity>`), so "find the chapters" must skip hidden sections and also react to style changes, not only to added or removed nodes (`components/game/useChapterSections.ts`).

## SplitText reveals without a flash

The Hero name (`components/chapters/hero/HeroScene.tsx`) is split into one `<span>` per letter with `SplitText.create(el, { type: "chars", tag: "span", aria: "hidden" })` and animated in. The trap is the _hidden_ starting state: the server HTML shows the name, so hiding the letters after hydration makes them blink out and back in. Rule used here: hide only when the animation is certain to run _and_ nobody can see the hide — while the splash reports `boot: "playing"` its overlay covers the Hero. If the splash never played (seen this session), the name was visible since the first paint, so it gets a hop that never hides it. The split is made inside the `useGSAP` context, so a revert restores the original text, and it is reverted after the intro (kerning comes back). `aria: "hidden"` + an `aria-label` on the `<h1>` keep screen readers from spelling the name letter by letter. Bio words use `aria: "none"` instead: a `<p>` can't carry a label, and word spans read fine.

## Draggable + Inertia stickers with a keyboard fallback

`Draggable.create(el, { type: "x,y", bounds })` moves an element with transforms; while it is dragged, Draggable feeds the InertiaPlugin velocity tracker, so `InertiaPlugin.getVelocity(el, "x")` gives px/s at release. Draggable's own `inertia: true` stops dead at the bounds; to _bounce_, the throw runs on a proxy `{x, y}` with `gsap.to(proxy, { inertia: { x: { velocity: vx }, … } })` and every frame folds the free position back between the walls (`reflect()` in `hero/stickers.ts`, a triangle wave). Keyboard: the stat stickers are real `<button>`s — arrows nudge (Shift = further), Enter/Space throws — and "Toss stickers" throws all of them. Easy to get wrong: a parallax wrapper and Draggable must not move the same element (two writers of `x`), so `[data-depth]` sits on a wrapper and `[data-sticker]` inside it; and focusable buttons can't live inside `aria-hidden`, so the container is `inert` + `aria-hidden` only until hydration.

## Flip for filter reorder

Flip = First, Last, Invert, Play: record where elements are (`Flip.getState`), change the layout instantly, then `Flip.from(state)` moves each element back to where it was with transforms and animates it to its new place. The catch with CSS-driven filtering (`:has(:checked)`) is timing: by the time `change` fires the radio is already checked, so the old layout can't be recorded. Fix in `journey/JourneyMotion.tsx`: once JS runs, the wrapper gets `data-filter` and the CSS follows that attribute instead of `:checked` — the script records the state, then sets the attribute. `absoluteOnLeave` takes leaving entries out of the flow while they fade, so the list never collapses mid-animation. The accordion (`journey/layout.ts`) uses the same idea by hand: instant layout change, then a `clip-path` on the card and `translateY` on the entries below make it look like it grew — no `height` animation.

## Stage hints once per stage

`components/game/useStageHint.ts`: one IntersectionObserver per stage (thresholds every 1 %) measures the visible part against `min(stage height, viewport)` — a 3 000 px chapter can never be 40 % visible by area. When it is ≥ 40 % visible, the splash is done and the save cookie has been read, a 600 ms timer opens the hint and `markHintSeen` writes the key into the cookie's `hints`. `completeStageHint(key)` (called by the sticker throw, the card flip, a tab or an accordion) closes it and stops it from ever auto-opening. `<StageHintHost>` owns the card: a 7 s timer paused while hovered or focused, ✕, and an always-present `role="status"` region (a live region must exist _before_ its text changes, or screen readers may stay silent).

## Draggable on a proxy + a ghost clone (drag-to-equip)

The inventory card itself never moves: `Draggable.create(proxy, { trigger: card })` drags an invisible proxy, and a cloned "ghost" follows it. On release we hit-test the four slots, then tween the ghost into the slot (or back home) and remove it. The real DOM never changes position, so React's tree and the layout stay untouched, and a failed drop can't leave a card stranded.

## `useGSAP` with dependencies: `revertOnUpdate`

When the `useGSAP` callback sets up listeners or Draggables and has `dependencies`, pass `revertOnUpdate: true`; otherwise a dependency change runs the setup again without reverting the previous one (duplicate listeners).

## Native `<dialog>` as a bottom sheet

`dialog.showModal()` gives focus trapping, Esc and an inert page for free; CSS positions it at the bottom on phones and `::backdrop` closes it on tap. No portal or focus-trap library needed.

## Avoiding hydration layout shift with first-paint CSS

Anything JS will collapse (accordions, branches) is collapsed by CSS from the first paint, keyed on the `data-lite` attribute the pre-paint head script sets. Without JS the attribute is missing, so everything stays open; with JS the server HTML already has the final heights and hydration changes nothing.

## Pinned horizontal scroll with ScrollTrigger

Scene A (`components/chapters/projects/ShowcaseMotion.tsx`) is the classic "scroll down, the row moves sideways" section, built in two halves. The **pin** is plain CSS: the wrapper is `(count + 1) × 100vh` tall and the stage inside it is `position: sticky; top: 0; height: 100vh`, so it holds still for `count × 100vh` of scrolling and then leaves by itself. ScrollTrigger's own `pin: true` would also work, but it inserts a pin-spacer only after hydration (deep links like `/#contact` would land 300vh off, a layout shift) and switches the stage to `position: fixed` in JavaScript, which can jitter when the browser scrolls on its own (keys, scrollbar). The **scrub** is ScrollTrigger: one `gsap.fromTo(track, { x: 0 }, { x: () => -distance, ease: "none", scrollTrigger: { trigger: wrapper, start: "top top", end: "bottom bottom", scrub: true, invalidateOnRefresh: true } })`. `ease: "none"` maps scroll to position 1:1. `scrub: true` (not a number) because Lenis already smooths. The function-based `x` plus `invalidateOnRefresh` re-read the distance after every refresh, and a `ScrollTrigger.addEventListener("refreshInit", measure)` re-measures the layout just before that. `offsetLeft`/`offsetWidth` ignore transforms, so the moving track and the scaled cards never skew the numbers. The active card comes from `onUpdate`: a focus line travels from the first card's centre to the last one's, and the nearest card lifts while the background layer tweens to its accent. `gsap.matchMedia()` only calls back while at least one condition matches, so an always-true `all: "all"` condition keeps the mobile (carousel) branch running too.

## Flip filtering

The project grid (`components/chapters/projects/GridFilter.tsx`) runs the FLIP steps against React's render cycle: in the click handler, `Flip.getState(cells)` records every card's box (**First**). Then `setFilters()` lets React commit the new `data-filtered` attributes, and the grid re-flows instantly (**Last**). A `useLayoutEffect` keyed on the filters runs before the browser paints and calls `Flip.from(state, { absoluteOnLeave: true, onEnter, onLeave })`. That puts every card back where it was with transforms and animates it home (**Invert + Play**). Things to watch: hide with a non-`!important` rule (`[data-filtered="out"] { display: none }`), because Flip briefly sets `display` inline on leaving cards to fade them out; finish a running flip (`progress(1)`) before recording a new state; and animate the `<li>`, not the card, so the hover tilt on the card never fights Flip for `transform`. Lite / reduced motion skip `getState`, and the grid just changes.

## Custom cursor with quickTo

`components/game/cursor/CustomCursor.tsx`: `gsap.quickTo(layer, "x", { duration: 0.12 })` returns a function that retargets one reusable tween. Calling it on every `pointermove` is cheap (no new tween per event), and the dot only moves with `transform`. The label comes from the hovered element: `data-cursor="VIEW"` (or "DRAG", …), automatic "PLAY" on videos and "OPEN" on external links, resolved with `closest()` only when the event target changes (`resolve.ts`). The native cursor is hidden through `html[data-hk-cursor]` only while the dot stands in for it. It comes back over text fields, iframes and outside the window. Magnetic buttons (`data-magnetic`) move through the CSS `translate` property, not `transform`, so their own `:hover`/`:active` transforms still work. What is under a still pointer can change (scrolling, a dialog opening), so the cursor checks again with `document.elementFromPoint()` shortly after scroll, click or Esc.

## Modal with parallel + intercepting routes

`app/(site)/layout.tsx` renders a `modal` **parallel route slot** next to `children`. Inside `@modal`, the folder `(.)projects/[slug]` is an **intercepting route**: when a `<Link>` (a client-side navigation) goes to `/projects/mindlens`, Next renders that page into the slot *over* the current page, which stays mounted, and the URL still changes. A hard load (refresh, shared link) never intercepts: the real `projects/[slug]/page.tsx` renders. `(.)` counts route segments, not folders: `@modal` and `(site)` are not segments, so `(.)projects` sits at the root level. Closing is `router.back()`. Two traps: a slot keeps its last state on soft navigations to URLs it has no page for (so `@modal/page.tsx` and `@modal/projects/page.tsx` return `null` to close it), and with Cache Components a closed modal is only *hidden* by React `<Activity>` — its effects clean up and re-run like unmount/mount, so per-opening work (scroll lock, focus, view count) lives in effects and animations start from explicit values. Bonus: metadata is resolved over every slot, so the intercepted page's `generateMetadata` sets the tab title while the modal is open.

## FLIP shared-element from a card

The card stores its cover's `getBoundingClientRect()` on click (`components/project/transition.ts`); the stage cover is laid out at its final place, and FLIP — First (card rect), Last (cover rect), Invert (a `translate + scale` that puts the cover back on the card), Play (animate to `none`) — makes it fly home with transform only. Here the modal panel opens out of the same rect with a `clip-path: inset()` reveal. Both are native WAAPI (`element.animate`) on purpose: two WAAPI animations created in the same frame start together, while a JS tween keeps its own clock and ran ahead after a long first render, so the cover landed before the panel opened. With the same duration and ease the flying cover stays inside the growing clip.

## Sandboxed live iframe with a timeout fallback

`<iframe sandbox="allow-scripts allow-same-origin allow-forms allow-popups" referrerpolicy="no-referrer">` runs the site without letting it navigate our page. The easy-to-miss part: a site that refuses framing (`X-Frame-Options: DENY`, `frame-ancestors 'none'`) still fires `load` — the browser loads its own error page — so the `load` event can't detect it. `components/project/deck/LivePreview.tsx` therefore asks `GET /api/frame-check/{slug}` first (the server reads those headers, `lib/framing.ts`), then inserts the iframe with a 6 s budget; refused, disabled, timed out or errored → a fallback card with the screenshot and "Open site ↗". The page is laid out at a real width (1280 / 390 px) and scaled into the device frame with `transform: scale()`.

## Dynamic OG images

`app/(site)/projects/[slug]/opengraph-image.tsx` exports `size`, `contentType`, `alt` and a default function returning `new ImageResponse(<jsx/>)`. Satori renders a CSS subset (flexbox only; every element with several children needs `display: flex`) to PNG. It needs TTF/OTF fonts — not the WOFF2 `next/font` ships — so the Google Fonts CSS API is asked for a subset (`&text=` with exactly the characters drawn), which comes back as a few-KB TrueType file when the request has no browser user agent; cached with `"use cache"`. File-based metadata only fills `openGraph.images` when `generateMetadata` leaves that key out, which is how a project's own og_image / cover still wins. For dynamic segments Next serves the image at `opengraph-image-<hash>`.

## Web Audio SFX without files

`lib/sound.ts` makes every sound effect in code: an `OscillatorNode` (square, triangle or sawtooth wave) feeds a `GainNode` whose volume follows an envelope (`setValueAtTime(0.0001)` → `exponentialRampToValueAtTime(peak)` in 5–12 ms → back to 0.0001), and `frequency.exponentialRampToValueAtTime` slides the pitch. A "sound" is just a list of such notes with start offsets (`{ f, to, at, dur, type, vol }`): the badge jingle is an E–G–B–E arpeggio, a battle hit is a falling "bip" whose pitch drops as the damage rises, the boss defeat is a sawtooth crash plus a chime. Everything goes through one master gain and a soft low-pass into `destination`; notes are scheduled on `audioContext.currentTime` (the audio clock, not `setTimeout`), so they stay in time even when the main thread is busy. No audio files means nothing to download and no licences. Easy to get wrong: browsers keep an `AudioContext` suspended until the page gets a user gesture. So the context is only created after one (`navigator.userActivation.hasBeenActive`, or a gesture seen by `unlockAudio()`), `<SoundHost>` resumes it from `pointerdown`/`keydown` listeners, and a note asked for while the context is still waking up plays only if it wakes within 200 ms. Otherwise a burst of stale sounds would play later. With sound off (the default) no context is ever created, and switching sound off suspends it.

## Badges as derived state

Six badges unlock where the action happens (`unlockBadge("tinkerer")` in the loadout code). The other four are facts about state the game already keeps: Explorer = every chapter bit set in `visited`, Collector = every featured boss id in `defeated`, Curious = 3 opened projects, Night Owl = the local hour is 0–3. Those are pure predicates in `lib/badges.ts` (Vitest-tested), and one `<BadgeWatcher>` re-checks them whenever an input changes (a store subscription on `visited`/`defeated`, the opened-projects counter, the tab becoming visible, local midnight). It doesn't scatter `if (allVisited) unlock()` calls over the chapters, so a defeat in the modal, on the full page or via Skip battle all count. An earned badge is then latched into the save cookie, so it stays even when the inputs later change (a newly featured project doesn't take Collector back). The same watcher decides what is _news_: it diffs `badges` between two store updates and only when the save was already hydrated on both sides. Badges restored from the cookie therefore never toast again, while one earned in the same tick as hydration still does. Easy to get wrong: Zustand calls listeners synchronously, and a listener that unlocks a badge triggers a nested update. Always diff the `(state, prev)` pair you were given, never a copy kept from an earlier call.

## Theme switching without a flash

A theme stored in `localStorage` is unknown to the server, so the HTML always arrives in the default (paper) theme. Applying it in `useEffect` paints the paper theme first and then flips — a flash on every load. Instead the pre-paint head script (`components/game/splash/prepaint.ts`, an inline `<script>` in `<head>`) reads `hackker_prefs` and sets `<html data-theme="hackker">` while the HTML is still being parsed, before anything is painted; CSS keys every colour off that attribute. `<html suppressHydrationWarning>` lets React accept an attribute it didn't render. Two traps: (1) the zustand store hydrates _after_ mount with its default `hackerMode: false`, so the component mirroring the store onto `<html>` must wait for `hydrated` or it strips the attribute the script set; (2) in development, Strict Mode's remount resets `<html>` attributes, so a layout effect re-applies the stored value (a no-op in production). The re-skin itself is pure CSS custom properties: tokens like `--paper` / `--ink` are redefined per kind of surface, and because custom properties inherit, a rule only has to name the surface (`.hk-menu { --ink: …; --paper: … }`), never its children. Values that reference other tokens (`--border: 2px solid var(--ink)`) are resolved where they are declared, so they follow a theme set on the same element (`html`) but not a redefinition further down. Tested by aborting every JS chunk and checking the attribute on the bare HTML.

## Konami code listener

`lib/konami.ts` is a pure matcher: it keeps the last N inputs and checks whether they _end_ with the sequence. A "reset to 0 on mismatch" matcher fails on ↑ ↑ ↑ ↓ ↓ … (the third ↑ resets it although the last two ↑ are a valid start); the suffix check doesn't, and a pause longer than 3 s clears it. The DOM side (`components/game/konami/HackkerMode.tsx`) maps `KeyboardEvent.key` to tokens (ignoring repeats, modifiers and typing in fields) and touch gestures to tokens (start→end delta: a clear swipe on one axis, or a short still tap). Listener order matters because the last key is "A", which the Battle Arena uses for Auto-fire: listeners on the same target and phase run in registration order, React runs layout effects in tree order, and this component sits before `<main>` in the site layout — so its capture listener on `window` is registered before the Arena's and can `preventDefault()` the completing "A", which the Arena and Training Dummy skip.

## 404 status with streaming/PPR

The status code goes out with the first byte. `notFound()` returns a real 404 only if it runs before anything is flushed; once a shell is streaming, Next can only add `<meta name="robots" content="noindex">` (a soft 404). With Cache Components a dynamic route serves a prerendered _fallback shell_ for params missing from `generateStaticParams` (header `x-nextjs-postponed: 1`): the layout is flushed at once with 200, then the page resumes — so `/projects/does-not-exist` answered 200 even though the page awaits `params` outside `<Suspense>`. `export const ensureStatic = "navigation"` requires the whole route to be static output; for an unlisted param Next then waits for the complete static render instead of sending the fallback, and `notFound()` there becomes a real 404. Unmatched URLs are simpler: the root `app/not-found.tsx` is prerendered once as `/_not-found` and served with 404 for every unknown URL. Because it renders inside the bare root layout, it wraps itself in the site layout component to get the HUD. Check statuses on `next build && next start` — dev renders everything per request and behaves differently. In dev, 404 pages are also rendered on the client, which logs a harmless "script tag while rendering" warning for the root layout's inline pre-paint script.
